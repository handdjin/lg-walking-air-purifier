# 공기청정기 이동 및 공기질 시뮬레이션

가상 주거 공간에서 공기청정기의 이동을 구현한 Python 모듈입니다. A* 알고리즘으로 벽과 장애물을 피하는 최단 경로를 탐색하고, 경로를 따라 한 칸씩 이동합니다. 공통 환경 모듈은 별도로 가상 시간과 방별 PM2.5 변화를 계산합니다. 두 모듈은 아직 자동으로 연결되지 않았습니다. Python 표준 라이브러리만 사용하며 별도의 패키지 설치가 필요하지 않습니다.

## 주요 기능

- 거실·주방·침실로 구성된 2D 격자 지도
- 벽·문·장애물을 고려한 A* 최단 경로 탐색
- 단계별 이동과 현재 위치·목적지·남은 경로 조회
- 이동 중 목적지 변경
- 잘못된 요청이나 도달 불가 목적지에 대한 오류 처리
- 1분 단위 공기질 계산과 재현 가능한 생활 활동 시간표
- 지정한 방에 대한 점진적 정화 효과
- 터미널 시연과 자동 테스트

## 실행 방법

`simulation/` 폴더가 포함된 프로젝트 루트에서 실행합니다.

```sh
python3 -m simulation.demo
```

거실 → 주방 → 침실 → 거실 순서로 이동하며 각 단계의 지도와 좌표를 출력합니다. 출력 사이에 대기 시간을 두려면 `--delay` 옵션을 사용합니다.

```sh
python3 -m simulation.demo --delay 0.2
```

`--delay`의 단위는 실제 시간의 초이며, 시연 출력에만 적용됩니다. 시뮬레이션의 가상 시간이나 물리적 이동 속도를 의미하지 않습니다.

테스트 실행:

```sh
python3 -m unittest discover -s simulation/tests -v
```

테스트는 경로의 최단 거리, 장애물 회피, 단계 이동, 목적지 변경, 오류 발생 시 상태 보존 등을 검증합니다.

## 지도와 좌표

기본 지도는 15열 × 11행입니다. 왼쪽은 거실, 오른쪽 위는 주방, 오른쪽 아래는 침실입니다.

```text
###############
#......#......#
#..XX..#..XX..#
#......D......#
#......#......#
#..X...########
#..X...#......#
#......#..XX..#
#......D......#
#......#......#
###############
```

| 기호 | 의미 | 이동 가능 여부 |
|---|---|---|
| `#` | 벽 | 불가 |
| `X` | 장애물 | 불가 |
| `.` | 방의 바닥 | 가능 |
| `D` | 문 | 가능 |
| `R` | 터미널에 표시되는 청정기 | 현재 위치 표시용 |

좌표는 `[x, y]` 형식입니다. 왼쪽 위가 `[0, 0]`이며, 오른쪽으로 x가 증가하고 아래쪽으로 y가 증가합니다. 지도 문자열은 `grid[y][x]`로 접근합니다. 이동은 상하좌우로만 가능하며 한 칸의 이동 비용은 1입니다.

방 영역의 `bounds`는 `[x_min, y_min, x_max, y_max]`이며 양 끝을 포함합니다.

| 방 코드 | 이름 | 도착 좌표 |
|---|---|---|
| `living_room` | 거실 | `[2, 4]` — 초기 위치 |
| `kitchen` | 주방 | `[11, 3]` |
| `bedroom` | 침실 | `[11, 8]` |

문은 `[7, 3]`, `[7, 8]`에 위치합니다. 문 칸은 특정 방에 속하지 않으므로 해당 위치에서 `current_room`과 `room_name`은 `None`이며, JSON으로 변환하면 `null`입니다.

지도 정의는 `house_map.json`에서 관리합니다. 화면을 구현하는 클라이언트는 `get_map()`의 반환 데이터를 사용해 시뮬레이터와 동일한 지도를 표시할 수 있습니다. 지도 변경 사항은 새 `Simulator` 인스턴스를 생성할 때 반영되며, 실행 중 지도 편집은 지원하지 않습니다.

## 사용 예제

```python
from simulation import Simulator

simulator = Simulator()
map_data = simulator.get_map()

# 목적지까지의 경로를 생성합니다. 현재 위치는 아직 바뀌지 않습니다.
state = simulator.move_to("kitchen")

# 호출할 때마다 한 칸씩 이동합니다.
while state["status"] == "moving":
    state = simulator.step()

print(state["current_room"])  # kitchen
print(state["position"])      # [11, 3]
```

위 반복문은 전체 이동을 검증하는 예제입니다. 화면에 이동 과정을 표시하려면 서버에서 일정한 간격으로 `step()`을 호출하고 각 단계의 상태를 클라이언트에 전달합니다.

## 인터페이스

| 함수 | 설명 |
|---|---|
| `get_map()` | 지도 크기, 격자, 범례, 방 영역·도착점, 시작점 반환 |
| `get_state()` | 현재 상태 사본 반환. 위치를 변경하지 않음 |
| `move_to(room)` | 현재 위치에서 목적지 방의 도착점까지 경로 예약 |
| `step()` | 경로가 남아 있으면 한 칸 이동하고 상태 반환 |
| `render_map()` | 청정기 위치를 포함한 터미널용 문자 지도 반환 |

초기 상태:

```json
{
  "current_room": "living_room",
  "room_name": "거실",
  "position": [2, 4],
  "destination": null,
  "status": "idle",
  "remaining_path": [],
  "remaining_steps": 0
}
```

| 필드 | 의미 |
|---|---|
| `current_room` | 현재 좌표가 속한 방 코드. 문 위에서는 `null` |
| `room_name` | 현재 방의 한글 이름. 문 위에서는 `null` |
| `position` | 현재 좌표 `[x, y]` |
| `destination` | 요청한 목적지 방 코드. 도착 후에도 유지 |
| `status` | 이동 중 `moving`, 남은 경로가 없으면 `idle` |
| `remaining_path` | 현재 칸을 제외한 다음 칸부터 도착점까지의 좌표 목록 |
| `remaining_steps` | 도착까지 남은 이동 칸 수 |

### 이동과 오류 처리

- 목적지 방의 영역에 들어온 뒤에도 지정된 도착점까지 이동합니다. 도착 여부는 목적지와 `status`를 함께 확인합니다.
- 이미 도착점에 있으면 같은 방으로의 요청은 즉시 `idle` 상태를 반환합니다. 같은 방의 다른 칸에 있다면 도착점까지 이동합니다.
- 이동 중 새 요청을 받으면 현재 위치에서 새 목적지까지 경로를 다시 계산합니다.
- 잘못된 방 코드는 `ValueError`, 도달 불가 목적지는 그 하위 유형인 `NoPathError`를 발생시킵니다. 두 경우 모두 기존 위치·목적지·경로를 유지합니다.
- 반환된 지도나 상태 사본을 수정해도 시뮬레이터 내부 데이터는 변경되지 않습니다.

## 서버 및 클라이언트 연동

### 이전 버전과의 차이

이전 방 단위 구현에서는 `move_to()` 호출 즉시 방이 변경되었습니다. 현재 버전에서는 **경로만 생성하며 실제 이동에는 `step()` 호출이 필요합니다.** 기존 서버에서 이동 함수를 한 번만 호출하는 경우 연동 코드를 수정해야 합니다.

`current_room`, `room_name` 필드는 유지되지만 문 위에서는 `null`을 반환하므로 클라이언트에서 해당 상태를 처리해야 합니다.

### 권장 연동 흐름

1. 서버 시작 시 `Simulator()`를 한 번 생성하고 동일한 인스턴스를 유지합니다.
2. 지도 요청에는 `get_map()`, 상태 조회에는 `get_state()`의 결과를 반환합니다.
3. 이동 요청으로 받은 방 코드를 `move_to(room)`에 전달합니다.
4. 서버의 단일 진행 루프에서 일정한 간격으로 `step()`을 호출합니다.
5. 클라이언트는 상태를 주기적으로 조회하거나 전송받아 `position`으로 위치 표시를 갱신합니다.
6. 문 위에서는 별도의 통과 상태를 표시하고, 목적지와 `status`를 확인해 도착을 처리합니다.

상태 조회 요청마다 `step()`을 호출하면 접속자 수나 조회 빈도에 따라 이동 속도가 달라집니다. 조회와 이동 처리는 분리해야 합니다. 또한 이동 과정을 표시하려면 하나의 이동 요청 안에서 전체 경로를 즉시 완료하지 않도록 합니다.

현재 모듈은 메모리에 상태를 저장하며 다중 스레드의 동시 상태 변경을 지원하지 않습니다. 단일 서버 프로세스에서 명령과 이동 단계를 순서대로 처리하거나 서버 측 잠금으로 동시 변경을 제어해야 합니다.

## 공통 공기질 환경

`environment.py`는 데이터 생성기와 이동 시뮬레이터가 함께 가져다 쓸 수 있는 환경 계산 모듈입니다. 사용한 농도, 오염 증가량과 정화율은 가상 환경을 위한 가정이며 실제 기기의 성능이나 건강 기준을 나타내지 않습니다.

```sh
python3 -m simulation.environment_demo
```

기본 수식의 결과, 무작위 활동 시간표, 동일한 오염 조건에서 정화 유무에 따른 농도 차이를 출력합니다. 비교 예제는 정화 계산 확인용이며 자동 제어 정책의 성능 평가가 아닙니다.

### 1분 계산 규칙

모든 방의 시작 농도는 10µg/m³입니다. 매분 오염 증가 → 자연 감소 → 정화 순서로 계산합니다.

```text
C1 = 이전 농도 + 이번 분의 오염 증가량
C2 = C1 - max(C1 - 10, 0) × 0.01
정화 중인 방: max(5, C2 × 0.95)
그 밖의 방: C2
```

요리의 증가량은 분당 3, 청소와 침구 정리는 분당 2입니다. 정화는 호출 시 지정한 방 한 곳에만 적용됩니다. 자연 감소는 농도가 10을 초과할 때만 적용하며, 10 미만인 값을 10으로 올리지 않습니다. 방 사이의 오염 확산은 포함하지 않습니다.

### 기본 활동 시간표

| 활동 | 방 | 시작 시각 범위 | 지속 시간 |
|---|---|---|---|
| 아침 요리 | 주방 | 07:00~09:00 | 10~20분 |
| 저녁 요리 | 주방 | 18:00~20:00 | 10~20분 |
| 청소 | 거실 | 13:00~17:00 | 5~10분 |
| 침구 정리 | 침실 | 07:00~10:00 | 5~10분 |

시작 시각과 지속 시간은 양 끝을 포함한 정수 분 범위에서 선택합니다. 활동은 `[시작, 종료)` 구간에 적용합니다. 같은 방에서 활동이 겹치면 증가량을 합산합니다. 환경의 난수는 전역 `random` 및 별도로 만든 방문 시나리오 난수와 독립적입니다.

### 사용 예제

```python
from simulation.environment import AirEnvironment

# 가상 하루의 00:00부터 시작합니다. day_index는 재현용 일별 번호입니다.
environment = AirEnvironment(seed=42, day_index=0)
scenario = environment.get_scenario()  # 데이터 생성 설정 보관용

# 실제 방문 상태가 거실이라고 확인한 경우에만 측정합니다.
current_room = "living_room"
observation = environment.sample_current_room(current_room)
# {'minute': 0, 'room': 'living_room', 'pm25': 10.0}

# [00:00, 00:01)의 환경을 계산합니다. 기본값은 정화 없음입니다.
minute = environment.advance()
# minute == 1

# 이번 1분 동안 거실에 정지한 청정기가 정화한다고 가정한 호출입니다.
minute = environment.advance(purifying_room=current_room)
# minute == 2

# 미래 정답·평가용 농도입니다. 예측 모델의 입력이나 앱 관측값으로 쓰지 않습니다.
truth = environment.get_ground_truth()
```

위 예제는 환경 함수의 사용법입니다. 실제 위치 검증이나 농도 기준에 따른 정화 판단까지 구현한 예제가 아닙니다.

### 환경 인터페이스

| 함수·속성 | 설명 |
|---|---|
| `AirEnvironment(seed=0, day_index=0, late_dinner=False, events=None)` | 하루 환경 생성. `events=None`이면 무작위 기본 시간표 사용 |
| `minute` | 00:00부터 경과한 가상 분. 초기 0, 하루 종료 1440 |
| `advance(purifying_room=None)` | 정확히 1분 진행하고 새 시각 정수 반환 |
| `sample_current_room(current_room)` | 지정한 현재 방 하나의 `{minute, room, pm25}` 측정 결과 반환 |
| `get_ground_truth()` | 정답·평가 전용 `{minute, pm25: {방 코드: 농도}}` 사본 반환 |
| `get_scenario()` | 규칙 버전·수치·시드·일별 번호·활동 시간표 사본 반환 |
| `calculate_pm25(current_pm25, emission=0.0, purifying=False)` | 상태를 저장하지 않는 단일 방의 1분 농도 계산 함수 |
| `generate_daily_events(seed=0, day_index=0, late_dinner=False)` | 하루의 생활 활동 4개 생성 |

`advance()`는 자동 정화 여부를 판단하지 않으며, 정화 명령을 다음 호출까지 유지하지도 않습니다. 정화를 계속하려면 매 호출에 방을 지정합니다. 이동 중이거나 정화하지 않을 때는 `None`을 전달합니다. 잘못된 방 코드는 상태 변경 전에 `ValueError`로 거부합니다.

### 시간과 관측 제한

- 현재 시각이 t이면 `advance()`는 `[t, t+1)`의 활동과 정화를 적용하고 시각을 t+1로 바꿉니다.
- 예를 들어 09:00~09:10 활동은 09:00부터 진행하는 첫 호출부터 09:09부터 진행하는 호출까지 총 10번 적용합니다.
- 측정과 정답 조회는 시간을 진행시키지 않습니다. 내부 농도는 반올림하지 않으며 표시할 때만 반올림합니다.
- 환경 모듈에는 청정기 좌표가 없습니다. 호출자는 실제 방문 상태로 검증한 방만 `sample_current_room()`에 전달해야 합니다. 이 함수 자체는 위치 접근 제한을 보증하지 않습니다.
- 이동 모듈과 연결할 때는 `Simulator.get_state()`의 실제 현재 방을 사용해야 합니다. 도착 시 측정 규칙에 맞춰 `status`와 목적지 도착 여부도 확인해야 합니다. 문 위의 `None`으로는 측정할 수 없습니다.
- 마지막 측정값·시각, 미측정 상태, 10분 간격 재측정, 도착 측정 중복 방지는 관측 기록을 관리하는 쪽에서 구현해야 합니다.
- 모든 방의 실제 농도를 반환하는 `get_ground_truth()`와 미래 사건을 포함하는 `get_scenario()`는 데이터 생성·평가 전용입니다. 이를 예측 입력이나 일반 앱 상태 응답에 포함하지 않습니다.

### 하루 경계와 데이터 생성

한 인스턴스는 독립적인 하루 시나리오입니다. 1440분에 도달한 뒤 `advance()`를 호출하면 오류를 반환하며, 자동 초기화하지 않습니다. 다음 날은 새로운 `AirEnvironment(seed=42, day_index=1)`처럼 생성합니다. 새 인스턴스는 모든 방을 농도 10으로 초기화합니다. 실제 앱을 자정마다 초기화해야 한다는 의미는 아닙니다.

데이터 생성기는 1분씩 환경을 진행하고, 방문·측정 기록은 별도로 저장합니다. 학습용 행은 10분 간격으로 구성하며, 첫 세 방 관측이 완료되기 전의 행은 제외합니다. 30분 뒤 정답을 붙일 때 다음 독립 시나리오의 초기화된 값을 사용하지 않습니다. 25,920개 환경 정답 행을 기록하려면 각 날짜의 0~1430분을 10분 간격으로 저장합니다. 날짜 경계와 초기 관측 조건 때문에 실제 학습 행 수는 이보다 적습니다.

`late_dinner=True`이면 저녁 요리의 시작 범위를 20:00~22:00으로 이동합니다. 다른 활동의 시각·지속 시간은 같은 시드와 일별 번호에서 유지됩니다. 시험 시나리오는 모델 성능을 확인하기 전에 선택해야 합니다.

재현을 위해 `get_scenario()` 결과와 실제 정화·방문 기록을 함께 저장합니다. 같은 시드, 일별 번호, 설정, 정화 명령을 사용하면 동일한 결과를 얻을 수 있습니다. 방문과 정화가 다르면 같은 오염 사건을 사용해도 농도는 달라집니다.

고정 시간표로 검증하거나 저장한 시간표를 복원할 때는 다음처럼 사용합니다.

```python
from simulation.environment import AirEnvironment, PollutionEvent

# 예제용 조리 이벤트입니다. 기본 생성기의 시간 범위와는 별개입니다.
events = [PollutionEvent("kitchen", "cooking", 540, 550)]
environment = AirEnvironment(events=events)

# events=[]는 오염 활동이 전혀 없는 하루를 의미합니다.
```

`PollutionEvent`의 시각은 0~1440분 안에 있어야 하며, 종료 시각은 시작보다 커야 합니다. 사용자 지정 시간표는 기본 활동 시각 범위 밖도 허용합니다. 미래 사건 시간표는 재현·평가용으로만 사용합니다.
